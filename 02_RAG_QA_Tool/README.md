# RAG Q&A Tool

A working retrieval-augmented-generation pipeline over PDF documents: real
pdfplumber text extraction, LangChain's recursive character chunking, a
FAISS vector index, and a grounded, cited answer generated by an LLM - with
every piece testable offline through a deterministic embedding fallback and
a mockable LLM interface, not just a wrapper around a hosted API.

**Achieved on the 3 bundled sample PDFs (insurance, leave policy, warranty
manual): 16 chunks indexed (800-char chunks, 100-char overlap, 5-6 per
document), a 1,422-term offline TF-IDF vocabulary, and correct top-1
retrieval routing for both test questions** - "How many days of annual leave
do employees get?" and "What does the laptop warranty cover?" each retrieve
from the correct source document (see Testing below for the full run).

## What it does

1. **Extracts and chunks PDF text** (`src/ingest.py`): pdfplumber pulls text
   page-by-page from an uploaded PDF (path, bytes, or file-like), then
   LangChain's `RecursiveCharacterTextSplitter` (800 chars / 100 overlap by
   default) splits it into overlapping chunks tagged with their source
   filename and index.
2. **Embeds and indexes chunks** (`src/vectorstore.py`): an `EmbeddingProvider`
   interface has two implementations - a real one wrapping
   `GoogleGenerativeAIEmbeddings` (Gemini) or the OpenAI embeddings endpoint,
   used automatically when `GOOGLE_API_KEY`/`GEMINI_API_KEY` or
   `OPENAI_API_KEY` is set, and a fully offline, deterministic TF-IDF-based
   fallback (`OfflineHashingEmbeddings`) used otherwise and in the test
   suite. Either way, vectors are L2-normalized and indexed in a FAISS
   `IndexFlatIP`, so cosine similarity search works identically regardless
   of backend.
3. **Retrieves and generates a cited answer** (`src/qa.py`): given a question,
   retrieves the top-k chunks from FAISS, builds a grounding prompt ("answer
   ONLY from context, else say 'Not found in document.'"), calls an
   `LLMProvider` (Gemini / OpenAI / a no-op that explains a key is needed /
   a `FakeLLM` test double), and returns the answer together with the exact
   chunks used as citations - so the UI, and the test suite, can always see
   the receipts behind an answer.
4. **Renders a polished chat UI** (`app.py`): sidebar for API keys and
   chunking parameters, a PDF uploader, KPI row (documents/chunks indexed,
   active embedding backend), a chat interface with persistent history, and
   a "Source chunks used" expander with the exact retrieved text and score
   under every answer.

## Architecture

```
02_RAG_QA_Tool/
├── app.py                          # Streamlit chat frontend (entry point)
├── data/
│   ├── sample_insurance_policy.pdf
│   ├── sample_leave_policy.pdf
│   └── sample_warranty_manual.pdf
├── src/
│   ├── ingest.py                   # PDF text extraction + chunking
│   ├── vectorstore.py              # embedding providers (offline + Gemini/OpenAI) + FAISS store
│   └── qa.py                       # retrieval + prompt + LLM call + citations
├── tests/
│   ├── conftest.py
│   ├── test_ingest.py              # extraction/chunking correctness + edge cases
│   ├── test_vectorstore.py         # embedding + FAISS retrieval correctness + edge cases
│   ├── test_qa.py                  # mocked-LLM pipeline, citations, no-key fallback
│   └── test_pipeline.py            # full pipeline against the real sample PDFs
├── requirements.txt
├── pytest.ini
├── .streamlit/config.toml
├── .gitignore
└── README.md
```

**Data flow:** `ingest.load_and_chunk()` (pdfplumber → `RecursiveCharacterTextSplitter`)
→ `vectorstore.VectorStore.build()` (embed → FAISS index) →
`qa.answer_question()` (retrieve → prompt → LLM → citations). `app.py` is the
only caller that wires a *real* LLM/embedding backend in by default (when a
key is present); every other caller, including the entire test suite, can
inject the offline embedding and a `FakeLLM` and exercise the exact same
code path with no network access.

## Setup

```bash
cd 02_RAG_QA_Tool

# 1. Create and activate a virtual environment
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 2. Install dependencies
pip install -r requirements.txt

# 3. Run the test suite (fully offline, no API key needed)
pytest -v

# 4. Launch the app
streamlit run app.py
# open http://localhost:8501
```

## Live LLM calls require an API key

Retrieval (ingest → chunk → embed → FAISS search) works with **zero**
external dependencies or keys, using the offline TF-IDF embedding. To get a
**generated, LLM-written answer** instead of just the raw retrieved chunks,
set one of these environment variables (or paste the key into the app's
sidebar, which sets it for the session):

```bash
export GOOGLE_API_KEY="..."     # Gemini - models/gemini-embedding-001 + models/gemini-2.5-flash
# or
export OPENAI_API_KEY="..."     # OpenAI - text-embedding-3-small + gpt-3.5-turbo
```

With no key set, `app.py` still indexes and retrieves normally and shows the
real source chunks; the "answer" field explains that a key is needed for a
generated response, rather than crashing or silently returning nothing.

**The test suite never calls a real LLM or embedding API.** `tests/test_qa.py`
and `tests/test_pipeline.py` inject `src.qa.FakeLLM` (a deterministic
function double) in place of `GeminiLLM`/`OpenAILLM`, and every test uses
`OfflineHashingEmbeddings` in place of the hosted embedding backends. A
handful of tests in `tests/test_ingest.py` need no mocking at all - they run
the real chunker against the real sample PDFs.

## Tech stack

Python, pdfplumber (PDF text extraction), LangChain (text splitting +
Gemini/OpenAI orchestration), FAISS (vector similarity search), scikit-learn
(offline TF-IDF embedding fallback), Streamlit (chat UI), pytest (tests).

## Testing

```bash
pytest -v
```

34 tests, all passing, covering:
- PDF extraction: non-empty real text from all 3 sample PDFs, expected
  keywords per document, bytes-vs-path equivalence, and a malformed-PDF
  input raising rather than silently returning garbage.
- Chunking: empty/short text, max-size tolerance on long text, exact
  overlap between consecutive chunks (verified character-for-character),
  and chunk-index sequencing per source document.
- Embeddings: offline TF-IDF vector shape/dimension consistency, unit
  normalization, calling `embed_query` before fitting raises, and an empty
  corpus is handled without error.
- Vector store / retrieval: the correct chunk ranks first for a matching
  query, descending score ordering, `k` larger than the number of indexed
  chunks is clipped rather than crashing, an empty store returns `[]`, and
  very short/empty chunks don't crash indexing or search.
- QA pipeline: citation attachment matches the retrieved chunks exactly, the
  prompt sent to the LLM contains both the retrieved context and the
  question, an empty vector store short-circuits to "Not found in document."
  **without calling the LLM at all**, and the no-API-key fallback returns an
  informative message instead of raising.
- End-to-end pipeline on the real sample PDFs: chunk counts per document,
  correct top-1 retrieval routing to the right source document for two
  distinct questions, and a full mocked-generation run with real citations.

The Streamlit app was additionally run headless
(`streamlit run app.py --server.headless true`) and confirmed to serve
successfully with no API key configured, with no server-side exceptions.
